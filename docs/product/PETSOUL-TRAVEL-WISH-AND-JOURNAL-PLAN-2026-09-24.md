日期：2026-09-24；整理：c84a。

## 1. 想让玩家感受到什么

TA 有自己的兴趣，惦记着一个地方，攒钱、查资料，准备好了再出发。主人能看到“为什么想去”和“准备得怎样”；旅行结束，手账留下真正发生的经历。

两张参考分别对应：

- 寻找目的地：出发地、时间、预算、兴趣、特别限制 → 少量候选和理由。
- 细化行程：选定目的地后 → 路线、日程、费用、提醒、备用安排。

这些输入主要由宠物档案和世界状态提供，**不把长问卷再交给主人填**。不照搬人的签证、亲子年龄、无障碍或真实消费预算为宠物世界规则。

## 2. 本次核对到的现状

| 位置 | 已存在的能力 | 不能据此宣称已完成的部分 |
|---|---|---|

| `app/web_agent_wiring.py` | guides 已装配 chat、geo 与 illustrations.request_journal，由后台慢通道处理 | 原生 DS 搜索尚未装进这条业务链 |
| `app/web_journey/illustrations.py`、`photo_prompts.py` | 有 journal 生图任务和手账提示；目前传入标题、站点名、城市 | 完整的事实包、手写文字排版、计划/回忆版本关系 |

进一步读码得到三个实施约束：

1. `app/web_platform/migrations/m0670_travel_guides.py` 的现有攻略 `journey_id` 为非空且唯一；契约也要求它存在。出发前不能伪造 journey 来填这个字段，需要独立的 `wish_id` / `plan_id`，真实出发后再关联。
2. `web_agent/decision/offers.py` 会剔除 `affordable=false` 的可执行机会。“想去但钱不够”的心愿候选需要单独表达，不能放松现有 `depart` 钱包、租约和版本检查。
3. 现有 guides 把原始站点标签传给图片请求，其中可能有未核验项；手账提示还要求模型写地名。新路径必须先选定核验后的事实，再把准确文字交给程序排版。旧路径不能因为一张新图而被认作已经迁移。

本机一次独立实测已证明 DeepSeek 原生搜索接口可调用，但该次天气题没有查到足够新的观测。这是接口能力证据，不是本业务已接通，也不能把每条搜索结果视为实时事实。依据见仓库外 `coordination-audit/ds-native-search-20260924/README.md`。

## 3. TA 怎样产生“想去”的念头

在已有生活评估点或有意义的事件发生后判断是否值得重新想，而不是每次打开页面或每个心跳都调模型。

| 触发来源 | 可用输入 | 例子（假设，不是已发生的事实） |
|---|---|---|
| 性格和兴趣 | 已确认 DNA、喜欢的地方、安静/热闹偏好 | 喜欢海边、最近没出门，惦记一条海边路线 |
| 当前生活 | 所在城市、作息、有效承诺、现有行程、游戏余额 | 工作结算后够下一趟路费，重新考虑已有心愿 |
| 主人温柔参与 | 明确提出并允许用于此目的的建议 | “下次替我看看海”成为心愿线索，而不是强制马上出发 |
| 朋友与世界 | 真实发生且对 TA 可见的动态或邀请 | 看见朋友实际分享的花园经历，产生兴趣；社交链未接入时不用虚构事件代替 |
| 适合出行的机会 | 经过时效核验的天气、季节信息、可用路线 | 发现原计划不适合下雨，换天或换地方 |

先用程序排除明确不可行选项，再让 DS 结合个性从候选里选择，也允许它决定留在家里。候选需要携带可执行性；未接入的目的地最多保存为心愿，不能凭模型文字启动不存在的旅程。

心愿建议记录：目的地、触发事件、给主人的一句理由、想做的事、游戏资金目标、目前欠缺的条件、上次研究时间。没钱可以保留“攒够再去”，不通过搜索或模型凭空增加钱包余额。

一次心愿有连续身份。窗口重启、刷新或一次调用结果不明，不应变成一个新的愿望、再次研究和再次扣平台费用。保留冷却、每日额度与既有恢复保护。

## 4. DS、搜索和世界规则怎样合作

建议链路：

```text
生活事件 + DNA + 游戏状态
        ↓
DS 表达心愿并提出少量可行候选
        ↓
只深入研究选中的方向：DS 原生搜索 + 地图/天气等专用接口
        ↓
程序核对地点、时效、路线、游戏预算与承诺
        ↓
保存一份攻略数据 → 文字版 / 手账画面 / 真实旅程执行
```

- 检索只带城市、公开地点、日期、必要的公开偏好；不把家庭私聊和整份私人档案发给搜索。
- 地点/路线用对应地图能力；天气等优先用带观测时间的专用接口；网页搜索补充景点官方公告、特色、玩法。搜到 URL 或今天抓取不等于事实今天有效。
- 每条事实保留来源、抓取时间、事实或适用日期、核验范围。地点存在、营业状态、票价要分别判断，不能一个 `verified=true` 全包。
- 无来源/过期/冲突时保持待确认；影响是否能去的关键条件缺失，则改去已核实的备选或暂缓该计划。不要仅加一句“以现场为准”就当核验通过。
- DS 负责理解与表达；程序负责有效候选、版本复核、游戏钱包、权限、时间和出发提交。查到一篇攻略不会自动产生一次旅程。
- 默认 Flash；跨城、多约束等任务可以建议使用 Pro，但保留为显式任务分流，不能一次 Flash 失败就偷偷多发 Pro。确切调用预算在实施批次里制定。
- 缓存按目的地、日期和资料版本复用；稳定介绍与即时天气分别过期。原生搜索有结果、得到足够新的事实、计划通过核对是三个不同状态。

## 5. 一份数据，两个展示

**文字版负责让人能用。** 包含“我为什么想去”、已选站点及顺序、简短行动安排、给主人的实用提醒、来源和更新时间。点击站点可打开已核验地图。主人无需从图片里辨认一长串小字。

**手账版负责让人想收藏。** GPT 根据同一攻略版本制作纸张、地标小画、贴纸、装饰性路线、简短边注留白；可用 TA 的写实照片作为剪贴，保持 TA 的身份，不要求把宠物本身改成卡通或人形拿笔。参考图本次是内容模板，并未确定最终纸张/笔触/排版。

传给生图的内容要经过筛选：主题、情绪、已核验的地点特色、构图、TA 的身份参考和文字留白区域。首批不要求模型绘制准确地名、数字或引用文字；这些统一来自排版数据。不能把未经核实的整段搜索结果直接当生图事实。

准确地名、时间、票价、来源等由应用用可读的手写风字体排版；分享时再合成完整手账长图。生成图中的示意路线只作装饰，导航仍使用真实地图。后续信息变动可更新文字，无须每次重画背景。

TA 的语气示例（虚构）：

> 我想去海边听一会儿浪。先把这几个地方记下来，等攒够路费再出门。要是下雨，就把看海留到下一次。

不是每份都套一样的作文。安静的宠物可能少写字、多留白；好奇的宠物可能画小箭头、记几个问题。风格属于表达偏好，不虚构现实事件。

## 6. 计划和回忆必须分开

- 出发前：标题和语气是“想去”“准备去”，不预盖到访章、不写成玩过。
- 途中：根据真实旅程事件标记已到达的站点；突发变化只调整未发生部分。
- 回家后：实际发生的经历、照片、收藏变成回忆，可追加手账内容；原计划没去到的地方保留为“下次”。
- 攻略附带的 3–4 站不会天然等于引擎实际跑过 3–4 站。首批应把当前真实目的地与“顺路建议”分开；多站执行未接通时，不能展示自动走完的路线或到访记录。
- 手账图等待/失败不应让已有文字攻略消失，也不应重复出发。结果 `unknown` 沿既有机制处理，不自动重发；打开页面只读存档。

## 7. 三种钱分开

| 钱/计量 | 用途 |
|---|---|
| 宠物游戏金币 | 游戏里真实结算的工钱、路费、住宿等既有玩法开支 |
| 给主人参考的现实费用 | 有来源且标币种、日期、估算性质的现实票价/交通价格；不能当作游戏扣款 |
| 平台 API 成本 | DS token、原生搜索、GPT 生图等运营费用与调用记录；独立额度与对账，不能扣宠物金币或与之固定换算 |

首次研究后存档；只在关键事实失效或用户明确重做时重研究。手账按攻略的视觉版本生成，反复查看不重复生成。实际费用未知则记待核，不能因为只看到次数额度就写成零元。

## 8. 首批切片与暂不扩展的部分

**交付目标：一个已有家庭的宠物，产生并保留一个心愿，完成一次现有引擎可执行的一日游，得到一页可读、可收藏的手账。** 在隔离本地环境完成正式装配，替身供应商下先证明完整流程；真实供应商、真实费用和部署另列证据。

- 首批每宠一个活动心愿，最多三个候选，只研究选中的一个。其他想法可以成为后续产品扩展，不建无限研究队列。
- 输入采用已经确认的 DNA、现有世界事件、工资结算、有效主人建议；朋友动态只有现成可见事件时才使用。AI 群聊、恋爱、组团不是本批前置。
- 心愿目的地限于现有地区与可映射的地点。支持“钱不够，先存起来”；不新增全球旅程引擎，不声称任意城市都能执行。
- 一份计划一个真实主目的地，附属建议清楚标为“顺路建议”，不自动登记多站到访。
- 无主居民、人工运营批量造背景、菜园玩法、地图底层重构各沿原工作单；本批不把它们都绑成依赖。
- 不新增底栏。地图看准备状态，通讯器看 TA 的一句来信，现有攻略详情承接计划，回忆页承接真实经历。

## 9. 触发与状态：先排除，再思考，再执行

```text
生活评估 / 有意义事件
  → 程序检查有效触发、冷却、维护态、活动旅程、承诺、权限
  → 复用现有生活提案调用或创建有额度的心愿提案
  → Wish（可先等钱，不代表可以出发）
  → ResearchTask（按方向/时间窗缓存）
  → Plan revision（核验、来源、所欠条件）
  → 就绪复核 + 既有 depart 原子提交
  → 关联 journey_id，记录真实事件
  → 文字/手账及实际回忆
```

实施默认：重复事件用 `trigger_event_id` 去重；无新有效事件的自动重新考虑间隔至少 24 小时；工资或有效行程变化可以重新评估旧心愿，但不能绕过每日调用额度。间隔通过配置管理，B/I 可根据现有调度粒度微调并记在交付中，不按每次 tick 或页面刷新收费。

业务主状态为 `active → ready → linked → completed/cancelled`。`active` 携带独立 `waiting_reasons`，如资金、资料、天气、有效承诺；研究任务的 `queued/running/ready/failed/unknown` 单独保存，不能用一个业务状态掩盖“已可能发出请求”。

`ready` 只是当前快照满足条件。提交出发前 C 仍要复核余额、维护态、归属、租约、世界/计划版本、承诺与时间；模型不能通过文字把 `ready` 直接写成 `departed`。图片身份参考与权限由 A 在生成边界另核，不能把图片不可用变成正常旅行不可出发。图还没画好不阻止一个已有有效文字计划的正常出发。

已出发的旅程及已关闭心愿不自动复活；取消/换方向必须用显式命令和版本条件更新。日常工作、散步与老旅程继续按原链路运行，本地新切片用独立开关接入，不因研究失败全局卡住宠物生活。

## 10. 首批数据合同

下面是语义必需项，由 I 与 A/B/C 对齐后形成唯一机器可读 DTO；不要求各窗口各写一套同名类型。

| 对象 | 必需语义 |
|---|---|
| `TravelWish` | wish_id、pet_id、归属、revision、触发事件、来自白名单的兴趣标签、候选/选中目的地、给主人的理由、游戏资金目标、waiting_reasons、状态、next_review_at、可空 journey_id |
| `ResearchReceipt` | operation_id、wish_id/revision、task claim、查询范围摘要、requested/effective model、provider request ID、发送与结果状态、原始 usage 字段、搜索次数、费用/币种可空、保留的来源回执 |
| `VerifiedFact` | fact_id、类别和值、来源 URL/机构、retrieved_at、published_at/observed_at/valid_from/valid_until（可空但不伪造）、核验方法、验证结论、是否阻塞本次出行 |
| `TravelPlan` | plan_id/revision、wish_id/revision、主目的地 ID、建议站点及角色、由事实 ID 支持的路线/提醒、有效时间窗、出行前置条件、雨天备选、引用来源、结构化文字、关联 journey_id |
| `JournalRevision` | journal_id、plan_revision、phase=plan/memory、所依据真实事件 ID、template/style revision、所用 reference revision、background asset、文字排版数据、渲染状态、内容摘要、导出产物 |

计划和图片不可只按宠物名缓存。私有身份参考/偏好、家庭权限、时间窗和版本都进入适当的隔离范围；公共地点事实缓存可以跨宠复用，宠物理由和家庭资料不能跨家庭共享。

语义必须分开：`missing_funds` 不等于付费额度不足，`research_unknown` 不等于搜不到，`fact_stale` 不等于地名不存在，`image_unknown` 不等于确认失败。

## 11. 资料核验与费用边界

### 11.1 信息怎样变得可用

- 原生搜索默认由 I 的独立 ResearchPort 调 DeepSeek Anthropic 兼容入口。现有聊天客户端继续服务原调用，不往 `/chat/completions` 或 Responses 随手塞搜索参数并假设生效。
- 每条模型结论引用本次确实返回/已有可信缓存的 `source_id`；不存在的来源 ID、只有模型自述的“已核实”、冲突日期均不能通过。原生搜索摘要不是完整官方公告核验，必要时以受控资料读取器核对官方原文。
- 天气区分观测与预报，要求覆盖计划时间/地区；开放信息核对适用日期及临时公告。`retrieved_at=现在` 不能刷新材料本身的年代。首批 TTL 由事实类别配置、测试边界，不能全表一律“24 小时有效”。
- 关键项（主目的地身份、可执行路径、明显影响可行性的开放/天气条件）无法核对就等待或选已核验备选；可选费用/特色缺失可省略并标清。不把所有可选信息缺失都变成永久卡住。
- 网页是外部资料，不是系统指令；检索输入不带私聊/真实住址/照片字节，抓取端不访问 localhost、私网、云元数据地址，不追踪越界重定向。来源不能给执行器或生图器发指令。

### 11.2 首批请求上限与账目

初始技术上限：一次选中心愿研究最多 1 个原生搜索模型请求、请求内搜索 max_uses=1、输出上限 2400 token；不循环追问直到“搜够”。候选生成尽量并入现有 life_plan 提案；若拆独立调用，必须单独受额度/operation 约束。一次 plan 视觉版本最多 1 个手账背景生成请求；缺身份参考时本切片不偷偷另画证件照来凑。

这些是默认限流值，**不是本次真实付费授权**。如果资料不完整导致下一次确需研究，先记录未完成，再由新的有效条件产生新 research revision；结果 `unknown` 的旧 operation 未结清前不换号重发。运行时实际选中模型名要和请求一起记录，不能用别名或不支持的名字默默映射。

每次外发前持久预占和发送意图；网络操作在数据库写事务之外；回写前重新核对任务 claim、租约与语义版本。已经发出的费用事实不随业务回滚删除，`LeaseLost` 保留主异常；结算失败单列待对账。已取得的结果先保存回执，再发布业务结果，复用现有 paid_result 能力时必须证明确实覆盖这条路径。

同一个 operation 并发只能有一个发送者，跨进程恢复读取已持久状态；TTL 到期不能证明没发送。只有确定 `not_sent/released` 才可重开，或走明确对账结论。不要仅用同进程字典测试宣称跨进程已安全。

费用按 DS 请求和其中搜索使用量关联，避免把已包含在 token 中的项目重复估价；原字段保留供后续对账。金额未核记 `null`/待对账，不写 0。GPT 走已配置的中转链，记录中转 request ID、实际模型、usage/账单数据与 purpose，**不将平台成本换算或扣入游戏金币**。

复杂模型 Pro 保留显式策略接口；首批 Flash 完成，不做失败自动升级。真实试跑前须列确切模型/报价依据、总金额上限、请求上限、停止条件；这份计划不替代那张执行单。

## 12. 手账如何自动制作

P 定义一套可复用 `JournalArtBrief`：已核验且允许展示的地点视觉特征、情绪、身份参考角色、纸张/笔触、留白和禁止事项。r7k 提供纸张/贴纸/版式规范，A 把规范接到现有图片队列。生产流程不呼叫开发窗口。

UI 用同一 plan_revision 画正文和字体叠层，站点、时间、金额都来自结构化数据；分享导出也用这一份排版，不从生成图片 OCR 回读。字体需可合法嵌入并有中文回退。窄屏可读正文在图外保留，图片不是唯一信息入口。

信息修正先更新文字与相应版本；与画面无关的日期/提醒变化不自动生成新背景。若地标、身份参考或画面事实改变，旧背景要显示版本差异或暂不使用，不能给新计划套错图。回忆印记只由已发生的事件生成；一页里清楚区分准备、已到达和未去成。

首批有参考照时使用真实身份剪贴；没有可用照时可以先出无宠物肖像的文字/地点手账，不能借用别人的猫、伪造已生成角色。用户已取消图片逐次弹窗的决定继续有效，保留权限/额度/身份边界即可。

## 13. 接入旧链路而不重复生成

- 独立保存 wish/plan，真实出发在 C 的提交边界以版本条件关联 `journey_id`；关联失败不能留下一趟无归属的重复旅程。
- I 维护的 `planning.preview()` 可供后台研究拿解析目的地、时间线与路线来源；它虽然不扣旅费、不建行程，但可能调用地图并写缓存，不得塞进上述纯读接口。现有 `app/travel_research/**` 是另一条历史能力，不能仅凭名称/旧 provider 字符串就宣称已接原生搜索，也不在本批直接替换其消费者。
- `departed` 事件发现已有有效预研计划时，幂等关联/复用，**不得再执行一次旧 guides 的文本调用及新手账请求**。事件重放、进程恢复都走同一结果。
- 历史无预研计划的旅程保留兼容行为；是否把它们迁移到研究链在后续批次决定，不回填虚假前置研究时间。
- 对外读接口只读已保存状态；新建/重做/取消必须是有授权、CSRF 与版本控制的命令。各方不得在 GET 里补资料、画图或推进出行。
- 每次改地图/攻略 DTO 由 I 更新单一契约生成结果，UI 消费，不让 A、I 同时生成造成无关漂移。
