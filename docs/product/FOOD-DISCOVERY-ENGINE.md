# PetSoul 寻味引擎：有自己口味，也记得你的伙伴

版本：1.2 · 2026-09-22，包含真实交通到达与接待偏好用途约束。用户要求将附件方案纳入 PetSoul 的产品特色。本文是 [总方案](PETSOUL-2.0-MASTER-PLAN.md) 的功能专题；首发规模、算法权重和字段是施工建议，接口待框架窗口统一冻结。当前只完成方案，没有实现引擎、验证推荐准确性或取得供应商数据使用授权。

## 1. 产品价值与体验位置

目标：**根据可用证据，判断某家具体分店的哪些菜值得尝试、适合谁，以及这趟旅行是否值得去。**

对用户的表达：**它有自己的口味，也记得你的喜好。**

寻味接入原有生活循环：主人经营家园支持旅行 → 宠物根据性格选店 → 地图抵达 → 店内点选与活动 → 通讯和星球圈留下故事 → 主人收藏现实用餐建议 → 实际用餐后的反馈改进口味匹配。食谱、寻味纪念物或地域资源可作为后续旅行带回物，但不能改变真实餐食品质判断。

入口放在旅途的“让 TA 挑一家”、店铺详情的“为什么选这里”、通讯中的推荐卡，以及主人收藏的现实路线。保留家 / 旅途 / 星球圈 / 通讯四个主入口，不增加第五个主 Tab。主人现实用餐偏好可在首次使用时轻量补充，不阻塞注册和建立伙伴。

宠物的自主选择与主人参与并存。推荐结果不会自动扣旅费、改变位置或替主人下单；确认到访仍调用统一 Journey / Visit 与经济服务。

与 [地图交通/一起听看](TRANSPORT-COMPANION-SYSTEM.md) 共享行程时间：宠物探索按门到门可行到达、可停留窗口和行程版本推荐，不只看飞机落地时刻。改行程/延误后重新核对营业、预算和赶路条件；不能为了这家餐厅缩短车程。主人现实用餐及复刻路线使用主人自己的出行日期、位置与时间，不能直接套宠物的时间表。机舱/餐车的虚拟餐食不形成真实品质证据。

## 2. 四个判断分开呈现

| 判断 | 回答的问题 | 不混入的内容 |
|---|---|---|
| 餐食品质证据 Q | 有哪些资料支持这道菜的制作、口感或表现？ | 装修、照片数量、距离、游戏奖励 |
| 口味匹配 M | 符合当前用餐者的偏好吗？ | 将“我不爱甜”直接变成“甜口品质差” |
| 本次用餐价值 V / 行程便利 L | 此刻预算、时间、路线和场景合适吗？ | 把绕路或赶车归咎于餐厅不好 |
| 证据把握 / 不确定性 U | 信息有多新、具体、独立，缺少什么？ | 模型的自信语气、虚构的大样本 |

向用户展示理由和未知项；内部排序分不包装成全城永久榜单或未经校准的“满意概率 93%”。分店的来源评分可以按平台分别展示，不直接混平均。

判断实体为：**分店 → 菜品 → 味道/制作特点 → 适合的人 → 用餐场景**。分店 ID 必须包含来源命名空间；跨供应商实体合并需有核对依据。总店证据不自动转移给分店，汤面好评不代表全部菜品，堂食与外卖分开。

味道特征包含甜、咸、辣、油润、香料、软硬、酥脆、汤汁浓淡；这些是特征。制作评价描述火候、口感、风味协调及一致性，两者分别保存。对具体方面提取评价，例如虚构评论“面有嚼劲，汤对我来说偏咸，服务很好，午饭等很久”，拆为面条口感、咸度及个人不适配、服务评价、历史午市等待记录。历史等待不能显示为实时队列。

照片可以辅助读菜单、识别可见菜品、摆盘和环境，不能证明香味、鲜嫩、新鲜度或卫生达标。生成的宠物探店照片、虚拟评价和游戏点赞一律不能成为真实餐食证据。

## 3. 数据来源、来源限制与事实边界

| 来源 | 允许承担的职责 | 需要保留的区别 |
|---|---|---|
| 地图 / POI | 分店、地址、类别、可用经营信息及来源评分 | 找到地点不等于分析过菜品 |
| 店方提供或授权菜单 | 菜名、价格、做法和可选项 | 商家自述不是独立口碑，价格有日期与币种 |
| 获准分析的评论 / 探店资料 | 提取对应分店、菜品与体验方面的证据 | 来源、时间、适用对象、实际取得样本量 |
| 主人实际用餐反馈 | 修正个人偏好、补充具有限定的观察 | 自报实际用餐不自动等于平台核验到店 |
| 合作体验员记录 | 补充首发区域的具体观察 | 披露合作，不要求好评，不能伪装独立消费者 |
| fixture / 虚拟剧情 / AI 图片 | 测试流程或表达宠物故事 | 永不进入现实品质证据池 |

接入任何来源先核实取得、展示、分析、缓存/保存及模型使用权限；未知权限的资料不进入分析或长期存储路径。读取权限不自动授予训练或衍生用途。实现独立来源策略，只有允许的操作才能执行；日志与解释也不能泄露禁止留存的原文。

截至本次官方文档核对：

- 高德 POI 2.0 提供餐饮评分、人均、特色等可选字段，但字段存在不代表已有全量评论或菜品分析；实际权限与返回覆盖仍要验证。[高德 POI 2.0 文档](https://lbs.amap.com/api/webservice/guide/api-advanced/newpoisearch)
- Google Places 返回的 reviews 最多五条，按相关性排序；userRatingCount 是地点评价总数，必须与实际观察样本数分开。不能用五条精选样本断言近期趋势或“分析了上千条评论”。[Google Place 资源](https://developers.google.com/maps/documentation/places/web-service/reference/rest/v1/places)
- Google 的一般条款和 Places 政策涉及保存、衍生、模型改进与署名限制；个别服务如 Maps Grounding Lite 另有受条件约束的 LLM grounding 权限。按实际产品和用途核实，不把一般 API 接入当作全部分析授权，也不把所有模型推理一概判为禁止。[一般条款](https://cloud.google.com/maps-platform/terms)、[服务专用条款](https://cloud.google.com/maps-platform/terms/maps-service-terms)、[Places 政策](https://developers.google.com/maps/documentation/places/web-service/policies)

自有或明确获准分析的资料优先支撑本引擎。高德扫街榜 API 尚未确认；榜单名次、普通 POI 评分、PetSoul 个性推荐分别标来源，不互相冒充。

资料不足时返回“找到这家店，但还不足以判断哪道菜值得专程吃”。没有菜品证据就不生成招牌菜，没有实时队列就不承诺等候时长。店铺照片没有授权或不可用时用明确原创场景，不假称真实内饰。

## 4. 两套偏好与两种使用模式

| 模式建议值 | 使用的偏好 | 产出的性质 |
|---|---|---|
| pet_virtual_explore | 宠物个性、探索倾向、氛围偏好、最近经历 | 虚拟旅行选店与故事线索 |
| owner_real_dining | 主人确认的甜咸辣、食材偏好、预算、可接受等待、同行人数 | 主人现实用餐建议 |

共用具备相应用途权限的事实资料，分别计算匹配与适用理由；主人偏好不能被宠物的虚拟饮食记录覆盖。宠物旅行考虑世界内旅费，现实用餐考虑真实价格与币种，两种预算不混算。

[注册接待](RECEPTION-ONBOARDING-MEMORY.md) 中产生的偏好，只有主人确认主体和相应用途后才能传入本模块；未确认推测和私人倾诉在检索前排除。不能把主人的“不爱甜”当宠物偏好、把宠物习惯当主人实际忌口，或把悲伤程度用于选店。撤回/纠正后对应偏好版本与推荐缓存失效。

“我想去看看，不过资料里说它偏甜，你可能更喜欢另一家”是合理表达。把“我在平行世界喝过”写成现实亲测或据此增加真实好评不成立。

现实用餐的忌口与过敏要求独立处理：已知冲突从合适候选中排除，缺乏必要成分依据时标记待核实，不能当作已满足安全要求或让模型保证无过敏原。相关私人偏好默认不公开，不能出现在星球圈或发给别人的评论里。本功能不提供现实宠物喂食建议。

## 5. 决策流水线

1. 根据地点、路线、用餐时间和需求召回有明确来源的候选分店/菜品，记录本次覆盖范围与数量，不声称全城最优。
2. 先处理硬条件：认错分店、确认关闭、明确超硬预算、赶不上后续行程或已知饮食限制冲突，不能靠分数抵消。未知营业/价格/成分单列状态，不默认满足。
3. 对允许分析的内容提取实体、味道、制作/服务/价格/环境方面、时间与适用场景。提取器输出结构化观察，不直接决定金币或奖品。
4. 按对应分店/菜品、时效、具体程度、来源独立性聚合证据；同一原稿的十次转载仍是一组来源，多个模型读取同一稿也不新增证据。可对重复或疑似推广降权，不仅凭模型公开指控商家刷评。
5. 分别计算 Q、M、V、L、U。营业与价格、口感观察有不同更新策略；无法取得代表性近期样本时不产生趋势结论。
6. 对当前合格候选真正按计算结果排序，然后赋 rank 和截取展示数；同分用稳定规则，例如分店/菜品 ID。不能先按上游顺序取前十，再算分却不重排。
7. 将低证据候选放入明确的探索组或待核实组，保留缺失项；缺失 Q 不默认填高分，也不直接填零制造“品质差”的结论。
8. 表达层只消费已选定结果与可引用事实。先给首选、再给备选和探索项；数量不足时如实少给，不强造三个选项。

对自有或获准分析的数据，可实验以下带先验的品质证据分：

```text
Q(r,d,a) = [κ × μ(g,a) + Σ(w_i × y_i)] / [κ + Σw_i]
```

r 为分店，d 为菜品，a 为评价方面，y 为该方面的观察信号，w 为证据权重。先验 μ 必须有明确参考组和依据；没有依据不硬造基线。该值是内部证据分，不是实际满意率。有效证据量与置信说明单独保留，不能因收缩得到中间值就声称证据充足。

证据充分且通过硬条件的候选可实验：

```text
S = 0.45Q + 0.30M + 0.15V + 0.10L − λU
```

所有项先归一化，缺失项不参与这条“证据充分”配方。权重、归一化、先验与 λ 是待校准配置，保存算法版本；这不是经验证的最优公式。可定义“专程寻味”“赶车快餐”等确定性场景配置，不让模型每次临时创造权重。框架 R0 不需要先实现或验证此公式。

## 6. 界面、事件与主人反馈

推荐卡显示：分店与具体菜品、为什么合适、何时不合适、未知项，以及可展开的出处/日期/覆盖范围。卡片可以由宠物用自己的语气介绍，仍需区分现实资料与动物世界的演出。

纯虚构的界面示例：

> “我记得你喜欢清淡。这家面馆的资料主要提到面条口感，汤底有偏咸反馈。它在你的午饭路线上；能否少盐、当天供应和排队情况还需要问店家。”

不能无依据写“老板答应少盐”“我亲口尝过保证你喜欢”。建议询问店方不等于店方已经承诺。食物图和场景动效负责体验，不补造味觉证据。

与主线的连接：

- 地图选定候选产生 recommendation_id；用户/宠物实际确认下一站后，Journey 服务创建 visit_id。建议生成本身不产生到访事实。
- 到店后的选择、活动和结束由同一个 visit / 世界事件管理。推荐过不等于去过，到店场景不等于主人现实消费。
- 通讯可以分享寻味理由，公开动态仅使用被允许公开的角色故事；不泄露主人私人饮食档案。
- 游戏里的菜谱、种子、勋章由统一奖励规则发放；赞助、返佣或掉落概率不进入现实品质证据分。商业展示另行明确标识。
- 主人“收藏这家”只记录兴趣。实际用餐后可选喜欢/一般/不喜欢，补充菜品与原因，不强制提供公开消费凭证。

反馈分类更新：“太甜”优先修正口味匹配；“太贵/等太久”修正场景价值；“店已关门”触发地点复核。单一自报不自动覆写已核验商家状态。奖励有效填写而不是好评；点击、点赞、生成图受欢迎均不能当成吃过后满意。

现实反馈进入独立事实来源流程，带 self_reported / verified 等清楚状态；只有符合权限和质量要求的观察才能影响共享证据。用户可编辑或删除自己的偏好与反馈，旧推荐快照不偷偷改成新的历史事实。

## 7. 工程边界与待冻结契约

建立独立 food_discovery 模块：**获准证据提取 → 确定性筛选/排序 → 有事实约束的宠物表达**。复用地点、行程、宠物画像与记忆服务，不继续向 street_rank.py 堆入全部业务，不训练新大模型、不用多个“美食家 Agent”投票替代证据。

建议目录：前端 PetJourneyWeb/src/features/food_discovery/；后端 PetJourneyBackend/app/food_discovery/。路由/公开 schema/仓储按现有分层接入；所有 API 经唯一 Web 客户端、所有公开契约进入共享 DTO。R0 创建插槽与接口边界，业务实现仍由用户安排。

| 契约建议 | 必备语义 |
|---|---|
| FoodPreference | pet / owner 对象分离，所属用户/宠物授权，明确填写与推断来源，版本；私人限制不进公开投影 |
| FoodEvidence | 分店及可选菜品、方面/观察、来源种类与独立来源组、时间、范围、观察样本数、可用操作/到期规则；禁止存储的正文不存 |
| FoodRecommendationRequest | 模式、本人授权宠物/行程引用、版本、门到门可行到达/停留窗口或主人现实用餐日期时间、当前场景、预算币种与硬约束；用户身份从会话取得，服务端重验范围 |
| FoodRecommendation | recommendation_id、分店/菜品、mode、Q/M/V/L/U 的可缺省结果、eligible / needs_verification / excluded、rank / 组别、理由、unknowns、允许展示的出处 |
| RecommendationProvenance | 生成时间、事实/偏好/规则版本、source_rating_count 与 observed_sample_count 分开、fixture/live 数据状态 |
| FoodFeedback | recommendation_id、本人实际用餐自报、菜品/原因、反馈时间与核验级别；不同于 visit_id 的虚拟到访 |

候选 API 仅作为统一契约编写输入：读取/更新私人偏好、请求推荐、读取推荐详情、提交实际用餐反馈；建议挂在统一 /api/v1/web/food 下，由框架窗口一次性冻结具体方法、路径和枚举。生成型请求经受控任务/限流；写入和重试有幂等标识，不能重复产生付费任务或反馈奖励。

输出不包含原始私密资料或禁止分发的原文。公共推荐只能使用允许公开的资料；不能凭推荐 ID 越权读取另一位主人的偏好。来源更新、偏好改变或行程变化后，按版本刷新建议；出发前重验预算与世界状态，防止过期推荐直接结算。

首发复用按权限可共享的地点资料和分析结果，只对用户匹配按需计算。缓存键至少区分资料/规则/偏好/模式；不混用不同用户结果，不无限留存限时内容，不在每只宠物饭点重新研究全城。

| H36–60 | 两种偏好得到可解释差异，接入一次地图→到店→通讯/公开故事，并保留现实攻略收藏入口 | fixture 对比能证明推荐准确率 |
| H60 后 | 冻结新范围，验证/修缺陷；不足部分明确降级 | 临近比赛继续扩大城市与评论抓取 |

R0 只交付统一契约、展示、接入与 fixture，不把收集数据、调用付费模型、完整算法研发强塞给框架窗口。后续食物模块负责人留空，由用户指定。框架窗口不能因为等待真实菜单或数据权限而拖延共享壳。

比赛演示建议增加约 30–45 秒：同一路线，切换“清淡/浓郁” → 看首选与理由变化 → 展开一条依据/一项未知 → 让宠物出发。它与原旅行故事共用入口，不再建立第二套独立演示。

降级顺序：去掉更多城市、在线评论提取、自动学习、复杂权重与大量食物素材；保留小资料集、双偏好、事实解释、未知项和旅行接入。若没有合格真实资料，只展示明确的“示例餐厅/演示数据”模式，不虚构真实商家口碑，也不自动变成在线真实推荐。

## 9. 验收反例与效果证据

实施时覆盖以下关键反例；本轮没有执行这些业务测试：

| 反例 | 应有结果 |
|---|---|
| 同名不同分店、同店不同菜、堂食与外卖 | 不串用证据，不能由店级均分编出菜级结论 |
| 增加漂亮照片、缩短距离、获得游戏奖励 | Q 不变；只允许对应体验/行程维度变化 |
| 自己生成十条虚拟好评或同稿转发十次 | 现实独立证据数不增加 |
| 总评价一千条，实际只取得五条精选 | 展示两个不同数量，不推断最近趋势 |
| 确认关闭/超硬预算/已知忌口冲突 | 不进入合适首选；未知不假装通过 |
| 候选上游顺序与分数不同、同分 | 按计算结果真实重排，稳定处理同分；排序后才截取 |
| 所有候选缺菜品证据或仅一个可用 | 不造菜、不硬给三个推荐；显示未知/探索/不足 |
| A 读取 B 的私人偏好或反馈 | 拒绝；公开故事不带私人饮食限制 |
| pet 模式虚拟吃饭后再次请求 owner 模式 | 真实品质证据不受影响，不形成自评循环 |
| 原定抵达推迟、换乘不可行、主人另一天复刻 | 推荐失效/重算，检查实际时间营业与路线；交通不被压短，主人用自己的时间上下文 |

后续真实效果与“按距离”“来源评分”“只按偏好”等基线比较，观察分店/菜品正确性、实际用餐后适配、行程可行与不确定性表达。按时间、用户和餐厅隔离评估数据，避免同一评论同时作输入和答案。需要先积累合格实际反馈，才能讨论校准、提升幅度或推荐准确性。

本轮交付证明方案已纳入产品和框架任务；不证明上述算法、资料授权、真实评价质量、现场 UI 或现实用餐结果已经完成。
