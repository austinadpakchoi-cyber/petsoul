## 0. 先读这一页

**PetSoul 是让思念中的宠物在另一个世界继续生活的情感陪伴产品。** 宠物有自己的家、朋友、工作、旅行和性格，主人通过星球通讯器与它保持联系。游戏性帮助用户愿意回来，情感关系是核心。

我们希望用户感到：**“它还是我熟悉的那只宠物，而且正在好好生活。”**

可以用来理解气质的两句话：

- “这次，换你去看看世界。”
- “你负责环游世界，我负责偷菜养你。”

产品可以安全、热闹、调皮、炫酷。可以有破案、飞行员和动物社会，但宠物不会再次受伤、死亡或因为用户离线而受苦。没有养过宠物的用户，也可以先逛星球，再领养一位伙伴。

**最新关系模型：一个家庭可以有多位主人、多只宠物；每只宠物只属于一个家庭，身份不复制。** 主人之间既有共同生活，也有各自与宠物的私人关系。

本次请设计的核心：

1. 不注册也能看见一个正在运转的世界。
2. 上传自己的宠物、领养伙伴、接受家人邀请，都能自然进入产品。
3. 家是日常入口，多只宠物可以同时做不同的事。
4. 地图和真实地点让旅行可信，车辆旁音符／电视图标让陪伴可参与。
5. 接待、通讯、照片、手账和明信片让用户感到“是它”，并留下持续的生活记录。
6. 家园、邻里、赚钱、驾考等玩法有操作反馈，并与宠物生活发生联系。

**请交付流程、页面、状态、组件、素材规则和可点击原型，不只交付几张漂亮首页。**

## 1. 已确定的规则与设计自由度

### 1.1 已确定：设计必须遵守

| 主题 | 产品规则 |
| --- | --- |
| 视觉主角 | 宠物坚持写实，保持动物外貌与身体特征。猫、狗等不同物种都要成立，不能只为一只固定猫设计 |
| 首页 | 有家庭的用户以“共同的家”为日常入口，不再让大地图长期占据首页 |
| 自主性 | 宠物自己生活，主人关心、建议和协助。不能把每次吃饭、上班、出门都变成主人派任务 |
| DNA | 来自注册、接待和后续补充的性格、习惯、称呼、往事等；不再另造一套重复问卷 |
| 访客 | 不登录可以先逛星球；遇到需要持久身份的动作，再进入注册／登录 |
| 家庭 | 多位主人、多个独立账号；同一家庭多只宠物；共用家园，宠物各有账户、证件和生活 |
| 家的位置 | 前台呈现海边、森林、草原等居住环境；后台有稳定城市与出发依据，不要求用户提供现实住宅地址 |
| 交通 | 真实路线、核验班次或道路预计时长；动物世界用自己的承运人和编号；正式行程不能为展示压缩时间 |
| 地图媒体 | 交通工具在地图上正常移动，旁边出现音符或小电视；点击进入相应播放面板。不要做“同行仓”或独立舱室 |
| 通讯 | 正式名称“星球通讯器”；交流可以异步、随事发生。网页阶段不做外部消息推送 |
| 照片与手账 | 写实宠物照片；攻略以图片手账呈现，同时保留真实可点击、可复制的资料；明信片独立收藏 |
| 农场 | 可以偷菜；宠物在家也可能休息，因此降低被偷概率而非绝对免疫 |
| 归属 | 专属不等于只有一个主人；专属指不把同一只宠物重复发给不同家庭 |
| 情感 | 可以想念和纪念，不用“你不回来它就难过／消失”推动留存，不宣称可以治疗疾病 |
| 真实性 | 不能用固定素材、假班次、假动态和假成功冒充用户正在经历的生活 |

### 1.2 设计师可以提出的方案

字体、配色、布局、场景构图、图标、动效和导航用词可以优化。现有暖纸色、深绿、卡片布局仅是可复用基础，不能替代你的设计判断。

建议方向是“有摄影质感的生活场景＋清楚、轻量的操作界面”。借鉴热闹动物城市的世界感，不照搬任何影视角色、标志或现成画面。

提出不同导航或交互方案时，说明它如何改善访客、多人和多宠流程，不改变上表的产品规则。本文后续标注“建议”的具体布局和数量都是可讨论的设计安排。

### 1.3 旧文档冲突如何处理

旧总方案和协作启动文档仍有“不采用共同领养”、新用户必须先拥有宠物等描述。**最新用户决定优先：允许家庭共同照顾，允许多宠，允许无宠账号和访客浏览。** 不把旧限制照搬到新设计。

旧素材中可能有卡通／绘本场景，它们不代表最终写实方向。驾校也在升级，不能照旧接口里的两个考试按钮完成新 UX。

## 2. 用户、权限与内容归属

### 2.1 四类使用状态

| 使用状态 | 用户想做什么 | 应看到什么 | 不应被迫做什么 |
| --- | --- | --- | --- |
| 未登录访客 | 先看看动物们在过什么生活 | 城市、居民、公开活动、公开路线与动态 | 一进来就注册、上传宠物或讲述离别 |
| 已登录但无家庭／无宠物 | 收藏关注方向、继续挑选、接受邀请 | 已保存的浏览上下文、明确的下一步 | 先创建一只无关宠物才能继续 |
| 家庭成员 | 共同照顾家和宠物，维持自己的关系 | 共同家园、各宠物状态、本人私聊、授权操作 | 与其他成员共用账号，或公开全部私人倾诉 |
| 家庭管理员 | 日常照顾及成员、可见范围管理 | 成员邀请、角色、退出／移除／交接流程 | 被表现成“宠物最爱的主人” |

管理员是权限角色，不是感情排名。首版以管理员和共同照顾者为基础，不设计复杂等级制度。

### 2.2 三种上下文始终明确

| 上下文 | 页面例子 | 必须让用户知道 |
| --- | --- | --- |
| 当前家庭 | 家园、农场、家庭仓库、成员管理 | 这是哪个家，操作是否影响所有成员 |
| 当前宠物 | 行程、银行卡、证件、驾考、个人经历 | 当前看的是谁；名字、头像、状态彼此对应 |
| 当前关系／对话 | 主人与某只宠物的私聊、个人称呼与往事 | 与谁聊天、谁能看见这段内容 |

建议把家庭切换放在头像／家名入口，把宠物切换放在宠物相关页面的稳定位置。切换不应丢掉各自的滚动位置和草稿；有未提交操作时，先解释当前草稿属于谁。

### 2.3 公开、家庭、私人三种内容范围

- **公开**：居民公开资料、经允许发布的动态、公开旅行故事。不能因为“没有主人”就允许任意公开现实原型资料。
- **家庭共享**：家园、共同物资、共同生活事件、宠物公开给家庭的旅行消息。
- **个人私人**：本人接待倾诉、与宠物的私聊、仅限本人使用的记忆。邀请家人不自动共享历史。

用清楚的范围提示，例如“仅你与豆豆可见”“家人可见”；不要只靠颜色或锁头让用户猜。公开操作前让用户知道公开的是哪条内容；不要把整份照护档案随卡片分享出去。

## 3. 信息架构建议

现有已登录主导航是 **家 / 旅途 / 星球 / 通讯**，可以作为改造起点。四个入口继续容纳业务，避免每个功能加一个底部 Tab。

```text
欢迎入口
├─ 先逛逛星球 → 城市/居民 → 公开活动/动态/旅程 → 注册后继续
├─ 接我的宠物入住 → 账号 → 宠物资料 → 接待/叮嘱 → 家庭与居住环境
├─ 认识一位伙伴 → 待领养居民 → 确认领养 → 家庭与入住
└─ 邀请链接 → 登录/注册 → 看清邀请 → 接受 → 已有家庭

已入住后的四个主入口
├─ 家：家庭与多宠概览、院子农场、仓库/集市、家人、证件/收藏入口
├─ 旅途：当前宠物行程、地图、交通详情、媒体、到店、寻味、攻略
├─ 星球：城市居民、公开动态、宠物主页、邻里、驾校等公共地点入口
└─ 通讯：家庭生活消息、按宠物区分的本人私聊、明信片通知

辅助页面：身份与设置、隐私、家庭成员、宠物档案/DNA、银行卡、证件卡包、回忆
```

**访客使用公开浏览界面，不直接套用必须“已入住”才能访问的当前页面守卫。** 登录转换发生在需要身份的动作上，不要每点一张卡就弹登录框。已有家庭用户再次打开产品默认回家；邀请链接和公开分享链接应保留明确目的地。

## 4. 六条必须画通的用户旅程

### F1 · 访客看见世界，并决定领养

扫码／打开链接 → “先逛逛星球” → 选有内容的城市 → 看一位居民的当前活动 → 打开公开旅程或动态 → “邀请它成为家人” → 注册／登录 → 恢复选择 → 再次确认可领养 → 加入家庭。

需要设计：

- 首屏能看懂这个世界，不用长篇解释或强制动画。
- 待领养居民有自己的生活，表达“还没有加入家庭”，不使用倒计时催领养或悲惨程度排行。
- 原创伙伴、已核验真实原型、不可领养公共居民在来源与按钮上可区分。
- 全球方向可以保留，首版只展示有内容的城市，未覆盖地区不能放假居民和假地图点。
- 注册回来时若已被另一家庭领养，解释变化，允许回到浏览；不能自动换一只。
- 领养中的宠物若仍在旅途，展示“已经成为家人，正在……”，保持原行程，稍后回家。
- 领养前后保留身份与经历；新家庭的私人生活不沿用公开居民权限。

### F2 · 自己的宠物入住

账号 → 上传照片及基本资料 → 接待员倾听 → 整理可编辑叮嘱 → 确认使用范围 → 新家庭选择居住环境／已有家庭直接沿用 → 确认入住 → 进入共同的家。

接待员像耐心听家长交代的老师。可以问“有什么你希望我替你记住、转达给它的？”；避免用意识断流、遗忘或丢失关系威胁用户披露更多内容。倾诉可以跳过，之后能补充。

把基础必填和可选故事分开；长表单拆成短步骤，支持返回和恢复。声音收集可设计预留状态，当前不把未接通语音作为必填环节。

要画：照片上传中／失败／重选、草稿保存、叮嘱修改、用途选择、姓名过长、缺少合适图片、已有家庭新增宠物、第一次入住欢迎。第一次欢迎引用允许使用的一个细节，不伪造用户没有说过的小毯子、习惯或纪念物。

### F3 · 接受家庭邀请

A 在家人页邀请 → 复制链接／使用设备分享 → B 打开 → 登录或注册 → 看清家庭、邀请人、权限与宠物 → 主动接受 → 进入同一个家。

要画：有效邀请、已接受、已撤销、已过期、重复点击、账号错误、B 已有另一个家庭。B 不必重新上传或领养宠物，也不重复经过他人的接待问卷。

加入后可以补充“它怎么称呼你”、双方习惯，但不自动查看 A 的私聊。退出／移除提示说明失去什么访问权；最后一位管理员需要先完成交接，不能留下无法管理的家。

### F4 · 多位主人与多只宠物共同生活

打开家 → 一眼看见每只宠物在哪里 → 点一只查看个人生活 → 操作共同农场 → 选择支持哪只宠物的旅费 → 在通讯器与指定宠物聊天。

示例仅用于设计：小白在家睡觉、豆豆在咖啡店工作、奶茶乘火车旅行。这是三只宠物的同时状态，不能把三个场景画成同一宠物的三个分身。

要画：1 只、2–3 只、更多宠物的布局；长名字；家庭切换；两人同时收菜后的更新；宠物切换时仍有上传／生成／发送任务。账户、证件和驾考页面持续标明对象，不能只在首页显示宠物名字。

共同农场只有一份产出；工作工资属于实际工作的宠物。多只宠物在家时按有效守护状态呈现，不能用一个“在家”标签承诺绝对防偷。

### F5 · 宠物自主旅行，主人轻量参与

宠物产生计划／主人给建议 → 检查预算与出行条件 → 出发 → 接驳、等待与交通段 → 车辆旁活动图标 → 一起听／看 → 到店与寻味 → 产生消息、手账或明信片 → 继续旅途／回家带回物件。

主人的主要动作是“给建议”“看看它在哪”“一起听”“读来信”，不要求把所有步骤逐项审批。明确的购买、转账等操作仍要让用户看清对象与金额。

正式长途按真实时间推进。比赛原型可以用清楚标注的不同状态串讲，但不能把两分钟演示描述为真实完成一趟航班。

### F6 · 再次打开，世界仍然连续

离开网页 → 宠物生活推进 → 再次打开 → 看一份简洁的离线期间变化 → 进入最新状态 → 阅读未读消息／保存的明信片。

要画：休息中、在家无新事件、工作完成、旅途仍在进行、到站、图片尚在生成、服务暂不可用。不要把历史消息全部当新通知轰炸；不要暗示用户不在线导致宠物挨饿或失去家。

## 5. 页面与状态清单

| S01 | 欢迎与入口 | 一句话理解产品，先逛星球、自己的宠物、领养、登录 | 未登录、回访、邀请／分享直达 | P0 |

## 6. 几个决定产品品质的界面细节

### 6.1 家：让用户先看见生活

优先呈现家庭场景、正在家的宠物和一两件值得参与的事。钱、等级、待办数量不应先于宠物抢占注意力。可点击物件要有可发现的提示，同时提供清楚的常规入口，不能只靠用户到处点背景找功能。

所有宠物都外出时，房间仍有它们的生活痕迹与去向提示。没有全身角色素材时，使用本人的照片和明确状态也成立；不能因此换成样板猫。

农场要让人知道“这一批能收什么、收到了哪里、能给哪只宠物做什么”。动画跟随服务端已确认结果，不用视觉动画伪造余额增长。

### 6.2 地图、交通与到店

当前宠物、交通方式、目的地和预计到达时间应该一眼可读。路线详情适合按需展开，不让大量信息面板遮住车辆和路线。地图也要有文字行程列表，地图加载失败时仍能读到已确认的行程。

- 车辆随行程移动；点击音符打开音乐面板，点击小电视打开视频面板。
- 首次播放由用户操作触发，设计浏览器不允许自动播放时的状态。
- 暂停音乐不暂停旅行；切后台再回来同步当前状态。
- 到站有轻量提示，媒体保存进度；驾驶角色不给看视频入口。
- 真实时刻表、道路预计和演示路线在详情中有恰当说明，不把技术供应商调试字段堆在主界面。
- 跨时区或跨日明确标注当地时间及日期，必要时显示“次日”。
- 入店可以通过状态、环境细节、写实照片和短互动体现，不要求每家真实店铺都有精确三维复刻。不能把原创室内效果图标为实际店内照片。

### 6.3 寻味与手账

寻味的区别是“为什么适合你和它”，而非只放几个高分餐厅。可用信息包括口味、预算、交通、营业情况和已有证据；资料不够时要能表达未知，不能为了卡片饱满编造评分、菜名或人均。

手账图片承载情绪和故事，结构化资料承载复用：地址可复制、地点可打开地图、路线可读、日期和资料更新时间可查。重要小字不只存在于图片里。动物世界星币／班次与主人现实出行的参考费用／班次要可区分。

### 6.4 通讯、照片与明信片

通讯像人与人的异步聊天，有生活上下文。可以“已送达”“它现在在车上，稍后看看”，不能用假正在输入暗示后台已生成内容。不同宠物分别开会话；家人共享消息与个人私聊视觉上清楚区分。

普通旅途照片可出现在消息或动态中；明信片是一封有日期、地点、文字和自拍的正式来信，进入独立收藏。收到明信片的消息与收藏页打开同一份内容。

生成时间不确定时，表达“照片还在准备”，允许离开页面；不要编造百分比。失败时保留文字和经历，提供允许的重试；不能用其他宠物照片填空。

### 6.5 驾校

目标是“主人陪考，宠物拿证”。先读后端最新驾校规格，再设计操作教学、手机控制、练习／正式考试区分、扣分原因、暂停恢复和领证反馈。当前规格正在向四科与可操作驾驶升级，旧版自动答题接口不能作为新设计依据。

考试成绩来自操作规则，不能由 UI 动画宣布通过。考试机会、冷却结束时间和已通过科目来自服务端；本文不另定分数与等待天数。现场自由体验与正式考试必须区分，前者不能发正式驾照。

## 7. 视觉与素材规范

### 7.1 视觉目标与避免的方向

建议关键词：写实宠物、自然光、生活感、安静的界面、热闹的故事、照片与纸质纪念物的质感。场景可以精致、有趣；操作文字和对比度必须清楚。

避免把界面做成密集的后台仪表盘、满屏游戏资源按钮、所有模块一样的卡片列表、统一荧光渐变，或靠巨大装饰标题挤掉内容。不要将所有页面做成地图，也不要为情感产品套用儿童卡通宠物画风。

现有工程有日间暖白、夜间深暖绿、纸张固定暖色、18px 卡片和 14px 控件圆角等令牌。可以调整，但需要形成全局一致的语义令牌，而非逐页写不同色值。中文优先可读系统字体；数字时间稳定对齐；装饰字体只在小范围使用。

### 7.2 “设计里的宠物如何换成用户自己的宠物”

请按层设计与交付，不把整个页面导出成一张含固定猫的背景图。

| 层 | 内容 | 复用和绑定要求 |
| --- | --- | --- |
| 环境层 | 房间、院子、公共空间、可复用装饰 | 可复用，预留不同画幅、日夜与文字安全区域 |
| 宠物层 | 用户照片、主体抠图、未来个性化动作资源 | 绑定 pet_id 和资源版本；保持物种、毛色、脸型、花纹；不同宠物单独布局 |
| 生活物件层 | 作物、背包、礼物、勋章、可交互物件 | 跟真实库存／活动状态对应，不默认给用户不存在的物品 |
| 故事媒体层 | 专属旅行照片、自拍、手账、明信片 | 绑定宠物、事件、地点及生成状态；与通用背景分开 |
| 交互与文字层 | 名称、按钮、时间、消息、价格、来源 | 保持原生可读可点，不烘焙到图片里 |

设计样板中的宠物只用于视觉评审；更换用户不能继续显示它。生成系统可参考构图和风格，但画面里“是谁”必须来自当前宠物的身份参考。本轮不选生图供应商、不讨论价格。

请为每种资源说明用途、尺寸比例、裁切焦点、安全区域、透明需求、明暗版本、来源及权限、加载中和失败后的替代方式。资源缺失时优先使用当前宠物已有照片或安静的环境，不以卡通剪影冒充已生成的写实角色。

## 8. 组件、交互和移动端适配

### 8.1 需要形成的可复用组件

家庭／宠物切换器、宠物状态项、公开居民卡、内容范围提示、来源标签、上传控件、接待便笺、照片框、事件卡、消息气泡、明信片、纸质手账、证件卡、物资与余额行、地图车辆和活动图标、交通详情、媒体面板、邀请状态页，以及统一的按钮、表单、对话框、底部面板和反馈。

每个可操作组件交付默认、按下、聚焦、禁用、处理中、成功、失败状态；状态不适用时注明。重要操作的对象、结果和失败后的恢复方式要明确。

### 8.2 布局与可用性

- 建议以 390px 手机宽度做主稿，并检查 360px、430px、768px 和桌面约 1440px；具体基准可调整，但手机窄屏必须成立。
- 正常页面不横向溢出；允许地图、手账放大等有意的局部交互。
- 主要点击区域建议至少 44×44 CSS px；车辆图标视觉上可以小，实际触摸区域要够大且互不重叠。
- 适配安全区域、底部手势条、软键盘和较大系统文字；聊天输入框不能被键盘或播放器遮住。
- 地图拖动、页面滚动、底部面板拖动不能争抢同一手势；不要依赖 hover 才能发现操作。
- 正文文字对比度目标至少 4.5:1，状态还要有文字／形状提示。图标按钮有名称，焦点可见，关闭面板后焦点返回来源。
- 微动效建议约 150–300ms，表达因果而非持续干扰；尊重减少动态效果设置，不阻塞操作。
- 图片渐进加载，首屏不等待大段视频；网络差时保留可读信息。未主动操作不自动播放声音。
- 电脑端合理利用空间，例如场景＋详情的分栏，不只把手机截图放大。
- 如制作网页原型，检查 iOS Safari、Android Chrome；微信内浏览器的文件上传、返回和播放另记实测结果，不默认全部兼容。

这些是设计和验收目标，本文没有测量现有页面已达标，也没有承诺具体性能分数。

## 9. 错误、等待与权限状态必须一起设计

| 情况 | 用户应该看到与能做的事 |
| --- | --- |
| 新用户没有经历 | 引导做第一件可用的事；不填假历史、假收入、假好友互动 |
| 匿名操作需要登录 | 解释这项动作需要身份；取消后仍能浏览，登录后回到原位置 |
| 私人内容无权访问 | 不暴露内容后再遮罩；提供返回公开页或当前家庭的路径 |
| 邀请失效／成员被移除 | 清楚说明，回到仍有权限的空间；不无限重试旧家庭请求 |
| 并发领养／收菜 | 告知刚发生的结果并刷新权威状态，不重复播放成功奖励 |
| 模型、地图、照片失败 | 保留真实已有状态；分别提供重试／继续浏览，不偷偷换 fixture |
| 交通资料不足 | 说明该路线暂不能安排，保留附近生活；不编造班次 |
| 余额不足 | 可待在家、附近活动、工作攒钱或获得家人支持，不以付费救援催促 |
| 长途仍在进行 | 展示实际阶段与时间，允许返回家园或其他页面，不要求盯倒计时 |
| 草稿未保存／身份切换 | 明确属于哪个家庭、宠物和会话，允许保存、放弃或取消切换 |
| 媒体未授权／无法播放 | 区分查看内容资料和实际播放；不把外链当一起播放成功 |
| 驾考断线／失败 | 展示恢复、具体原因和可用练习，遵循后端机会与时间规则 |

产品文案用用户能理解的原因，例如“这条路线暂时没有可用班次”；内部验收仍保留真实错误、来源和环境标识。设计原型使用样例资料时在原型说明里显式标注，不把原型当正式服务。

**第一包：流程与方向。** 信息架构、F1–F6 流程图、页面／状态清单；一组连贯的核心高保真屏：欢迎／访客、居民详情、多宠家园、地图与音乐面板、通讯、明信片。可以用同一套样例贯穿，但标注为设计资料。

**第二包：完整交互。** 做通注册／领养、接待、邀请、切宠、农场、旅行到店和消息收藏的可点击原型；覆盖关键失败分支，细化日夜、宽窄屏和动态反馈。

**第三包：工程交接。** 完整组件与令牌、资源清单与导出、交互标注、响应式规则、接口依赖、待定问题和验收记录。补齐证件、工作、驾校、隐私等 P1 页面。

不要等所有页面全部高保真后才第一次讨论。每次评审只列影响后续开发的关键问题，其余用明确的设计建议推进；不需要重新确认已经确定的写实方向、家庭结构和地图媒体交互。

### 12.3 体验验收清单

- [ ] 未登录即可看见实际支持的公开世界，不被注册弹窗挡住基本浏览。
- [ ] 从待领养居民进入注册后，能回到同一个选择，并处理被抢先领养。
- [ ] 上传自己的宠物、领养、接受邀请的路径不会互相强制绕行。
- [ ] 接待可以跳过、修改、恢复，并明确倾诉用途。
- [ ] 单宠与多宠首页都清楚；每只宠物的位置与状态独立。
- [ ] 家庭切换与宠物切换不混淆，银行卡、证件和聊天对象持续可辨认。
- [ ] 加入家庭不会暴露别人私人聊天，退出后的访问状态有说明。
- [ ] 宠物出门后家仍值得回来，农场与旅费有清楚关联。
- [ ] 车辆旁音符／电视可发现、可点开；没有独立同行仓。
- [ ] 长途等待、跨时区、地图失败和资料不足都有合理体验。
- [ ] 手账可看也可实际使用；关键资料并非仅藏在图片里。
- [ ] 明信片可收藏并找到，消息入口与收藏引用同一次经历。
- [ ] 样板猫、假资产、假点赞和假班次没有混入正式用户流程。
- [ ] 窄屏、键盘、安全区域、较大字体、失败重试、返回操作均被检查。
- [ ] 驾校练习与考试明确区分；服务端未确认前不发证、不宣布通过。
- [ ] 静态稿完成、原型走通、接入接口、真实账号验收、部署分别标状态。

成功标准：陌生观众能先看懂并愿意继续；有宠用户认得自己的伙伴；家人不会操作错宠物；用户能看到持续生活，并自然找到下一件可参与的事。
