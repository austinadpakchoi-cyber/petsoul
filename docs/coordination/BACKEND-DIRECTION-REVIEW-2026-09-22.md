## 3. 已复现：撤销权限与写入之间存在并发窗口

### 位置与影响

当前 `app/web_household/service.py` 的 `create_invite()` 在约第 220 行先调用 `require_household(..., Action.manage)`，随后才用另一个数据库连接写邀请。成员有效性校验没有与该次写入绑定到同一个事务。

因此两个合法请求发生以下交错时，会出现撤销已提交，但依赖旧权限的新邀请仍创建成功的情况：

1. A、B 原本都是家庭管理员。
2. A 发起创建管理员邀请，读取权限成功，暂未写入。
3. B 移除 A，事务提交，A 已失去家庭访问权。
4. A 原请求继续，写出有效管理员邀请。
5. C 接受该邀请，成为家庭管理员；A 自身仍已被移除。

探针通过一个可控调度 hook，把步骤 3 安排在原服务的权限检查与写入之间；移除、创建、接受均调用实际服务方法，没有修改业务实现。结果为：

```text
A_still_has_access = false
C_role = admin
accepted = accepted
reproduced = true
```

这是接入前需要修正的权限撤销一致性问题；目前尚未证明线上存在可利用入口，不能把它表述为已发生的生产越权。

### 建议修正

- 在同一个写事务里重新核对执行者当前的成员状态和角色，再创建邀请或修改家庭。
- 可复用现有 `_access(conn, ...)`，在适当的写锁／版本条件下校验，避免先检查后开启另一个写连接。
- 同时检查 `set_role`、`remove`、`update_settings`、邀请撤销以及后续消费操作中的同类边界。当前只对创建邀请交错做了复现，不能声称其他路径全部已复现。
- 回归应保留同样交错：撤销生效后，旧权限不能继续产生新的权限凭证。普通顺序请求、重试、最后管理员保护也要保持成立。

## 6. 建议继续顺序与完成条件

**先做成一个新家庭的完整体验，再扩大城市和玩法。**

1. 修正并发授权边界，接入统一家庭／宠物授权。逐项替换旧单主人判断，包含图片、私聊、账本、证件、驾考、后台任务，不只改新路由。
2. 用 A 新建家庭与两只宠物，邀请 B；A/B 同看家园，各自私聊，选择正确宠物操作；C 无权访问；退出与并发结算保持一致。
3. 贯通匿名浏览、已登录无宠、待领养居民生命周期与注册返回。领养前后身份和历史连续，在途领养不瞬移。
4. 将官方船班实际接入计划：匹配出行日期、接驳、候乘、跨日、动物编号、票据、消费与位置。过期或缺资料时不回落到假班次。
5. 完成独立时钟推进、重启恢复及真实供应商的有界验收，最后再做前端新账号联调与部署准备。不能靠 seed 预填经历代替上述验证。

目前没有理由要求全面重做或中断当前方向；需要的是完成迁移与接线，并用新用户路径验收，而不是继续增加独立玩法。
